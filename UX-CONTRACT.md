# SDP Inventory UX contract

Business source: `docs/phase-1.md` plus the user's approval of all phases, correction to one production location, removal of pricing, fixed Shindengen identity without a Company details editor, and the tools/jigs request workflow with restricted user access. Visual source: `DESIGN.md`; runtime tokens: `src/styles.css`. English internal operations UI; UTC storage and the retained company display timezone. Inventory tracks quantities and stock status without price, cost, currency entry or monetary reports. Accessibility target: WCAG 2.2 AA; do not claim full compliance from automated checks.

## Canonical UI Map

No bulk row selection is shipped. Tables use server pagination and persist committed search, filters, sort and page in URL parameters. Page size defaults to 12. Search debounces 300 ms, ignores IME composition, clears immediately with a labelled clear control, resets page and passes cancellation to fetch. Lists distinguish loading, empty, no results and error with Retry.

Create/edit item returns to Inventory, announces success and invalidates data. Cancel/back preserves list query state; dirty forms use an app-owned discard dialog. Archive requires zero stock, confirms by item name and can be undone by Restore. Stock changes are pessimistic, require a reason and use a stable per-attempt idempotency key. Version conflicts keep the dialog open and refresh balances. Failed mutations retain all input and expose inline recovery.

Admin/Manager inventory rows expose Edit item and Archive item directly; archived rows expose Restore item. `src/components/ItemLifecycle.tsx` owns the shared archive confirmation and archive/restore mutation for both list and detail. Row edits preserve the list URL on return. Archive/restore preserves filters and pagination, refreshes affected views after server confirmation, and moves focus to the inventory summary if the row leaves the current results. Archival failures remain in the dialog for correction or cancellation.

Regular users use the Staff role: their landing page is Tool requests, with only their own requests and the active tool catalog available. Catalog/detail show the existing item photos and available quantities. Staff cannot change stock, upload photos, edit items, view global movements/serial history, export reports or open administration routes. The server enforces these restrictions independently. Managers retain catalog, photo and stock operations and may submit/view/cancel their own requests. Viewer remains read-only. Admins see all requests and alone approve, reject, issue and record returns. Admins may reject a pending or approved request before issue, including withdrawing approval when stock can no longer be supplied.

`src/components/ToolRequest.tsx` owns the shared request form, item photo and status badge; `src/pages/Requests.tsx` owns monitoring and action dialogs. A request specifies one item, whole-unit quantity and purpose. Pending/approved requests do not reserve or deduct stock; Admin issue records the actual handover and quantity. Users may cancel their own pending/approved requests; issued records are retained, and Admin-recorded returns replenish stock. Partial issue is final for that request; requested and actual issued quantities remain visible separately. Partial returns keep the outstanding balance visible. Serialized issues/returns require one serial per unit. Actions use versions, stable retry keys, disabled/busy controls, server-confirmed success and retained input after failure. Successful actions refresh quantities and move focus to the list summary. Search/status/page/notification request selection persist in the URL.

Requests, monitoring totals and request notifications poll every 20 seconds while active. `src/components/RequestNotifications.tsx` owns the header badge and accessible notification dialog. The count announces updates in a polite live region; it distinguishes checking/unavailable states from zero unread. Notifications link to the selected request; read controls and retry errors remain available in the dialog. Inventory/photo management continues to use the shared existing item gallery; request images refer to the same server-owned assets.

Dialog owns focus containment, initial focus, Escape, inert background and restoration. Confirmations focus the safe action. Toasts appear in a fixed bottom-right live region and never hold the only error message. Shared buttons implement hover, focus, pressed, disabled and busy states. Forms use noValidate and first-invalid focus; secrets stay masked with a show/hide control. Native selects/dates intentionally accept platform rendering. Textareas cannot be manually resized and use sufficient minimum height.

Login refreshes a session through an HttpOnly cookie; access tokens remain in memory. When authentication fails, preserve non-secret drafts and route to sign-in. Do not cache one user's data across logout. Role-restricted navigation is hidden and protected routes show a permission message; backend remains authoritative. Item drafts are scoped to the current user in sessionStorage; never persist passwords/tokens. Logo settings are Admin-only, including their API endpoints. Company identity is fixed to SHINDENGEN ELECTRIC MFG.CO.,LTD. Settings has no Company details form or save action; the retired details mutation rejects changes, and existing production-name/timezone values are retained.

All routes set `SDP Inventory | {Page}`. Mobile navigation uses a dialog drawer, inventory becomes cards, and desktop tables keep semantic headers. Every image has dimensions/alt policy; public brand assets use a shared resolver with a text fallback. The bundled Shindengen logo appears in login, full navigation, emails and reports; collapsed navigation and browser icons use the original website mark. Dark surfaces display the original blue logo on a white backing plate. Removing a custom upload restores bundled Shindengen artwork. Light/dark modes retain status meaning. No manufacturing-order or transfer workflow is included.

Verification: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`, `npm run test:e2e`, `npm run test:a11y`, `npm run format:check`. Tests exercise login, create/edit, stock in/out, nonnegative stock, filters, archive, roles, branding, hostile uploads, stale versions and failure recovery. Browser evidence lives in `tests/e2e`; backend evidence in `tests/api.test.ts`. Review sibling Inventory and Movements pages for visual/behavioral consistency.

The confirmed handover state is labelled **In use** in the request badge and filter; its existing API value remains `issued`. The in-use quantity is actual issued minus returned units. Approval alone does not mark tools in use. Excel sample imports retain original IN-USE counts as dated source reference without assigning them to invented borrowers. Available sample opening stock uses SPARE + STOCK, never TOTAL or IN-USE. Existing items and stock are preserved on repeated imports; mismatched source totals are reported.
