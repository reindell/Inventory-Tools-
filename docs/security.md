# Security review and operations

## Controls implemented

| OWASP area                  | Implemented control                                                                                                                                                                                  | Evidence / remaining boundary                                                                          |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Broken access control       | Bearer verification plus enabled account/session checks, server-side roles, owner checks on imports, Admin-only branding/users/audit                                                                 | API role and revocation tests; verify real production proxy topology                                   |
| Cryptographic failures      | bcrypt cost 12, hashed refresh/reset/invitation tokens, short-lived access JWT, secure production cookies, TLS proxy                                                                                 | Actual server certificates and backup encryption require operator configuration                        |
| Injection                   | Zod DTOs, parameterized SQL, fixed sort/table allowlists, React encoding, HTML mail escaping, CSV formula neutralization                                                                             | Hostile identifiers, duplicate identities and spreadsheet cells tested                                 |
| Insecure design             | Nonnegative stock DB checks, required versions, atomic row locks, UUID idempotency keys, immutable ledger/audit/request-history triggers, final-Admin protection                                     | SQL Server API/borrowing tests cover concurrency; target-server load testing remains a deployment gate |
| Security misconfiguration   | Helmet/CSP, same-origin API, exact Origin plus signed CSRF cookie/header, no credentialed wildcard CORS, private bucket, fail-closed production config                                               | Trust exactly one reverse proxy; never expose the app port directly                                    |
| Vulnerable components       | Lockfile, dependency audit, bounded and isolated image processing                                                                                                                                    | Scan OS/container images on the target server; dependency scans do not cover images                    |
| Authentication failures     | Five failed attempts cause 15-minute lockout, IP rate limiting, bcrypt timing for unknown users, refresh rotation/reuse family revocation, one-use recovery links, access revocation on user changes | Distributed rate limiting is needed before replicas; monitor failed jobs and lockouts                  |
| Software/data integrity     | Versioned transactional migrations, database constraints, audit/outbox in mutation transaction, image signature verification and re-encoding                                                         | Protect build pipeline, image registry, migration credentials and backups                              |
| Logging/monitoring failures | Structured request IDs, no request body/credential logging, sensitive-action audit, health endpoints and failed-job state                                                                            | Add central log collection, retention and alerts for server outages and failed delivery                |
| SSRF                        | No user-provided URLs fetched; SVG structural allowlist rejects URLs/references/styles/entities; controlled storage/SMTP destinations                                                                | Restrict container egress at the server firewall; only admins configure environment endpoints          |

The checks are engineering evidence, not a certification or penetration test. Automatic accessibility and dependency scans likewise cannot establish complete compliance or absence of vulnerabilities.

## Files and branding

Logo source limit: 2 MiB; PNG/WebP signatures or restricted SVG; maximum 4096 × 4096. Item source limit: 10 MiB; PNG/JPEG/WebP; maximum 25 megapixels. Reject animated/malformed media. Decoder output strips metadata. Uploads use random UUID names in private storage; no user HTML/SVG is served. Image URLs expire after 15 minutes and must not be logged or shared beyond intended recipients.

At most two multipart uploads may be buffered/processed at once per app process; excess requests receive 429 before the multipart parser allocates file buffers. Image decoding also has its own two-worker cap and timeout. Normal UI uploads run sequentially and show retryable errors when the service is busy.

An Admin replacement publishes a versioned brand pointer and audit event atomically. The file upload is outside the database transaction; failure cleans up newly written objects. Removed item images are queued for deletion after 24 hours so immediately outstanding signed URLs do not break. Prior logo assets remain retained, not automatically destroyed. Configure a reviewed retention policy and encrypted backups for both object storage and SQL Server.

## Tool-request access

Staff accounts can browse the catalog/photos and manage their own requests and notifications. The API rejects direct stock operations, catalog writes, global stock history, reports/exports and Admin endpoints for Staff; hiding navigation is an additional UI measure. Request lists and notifications scope data to the authenticated owner, while Admins can monitor all requests. Managers retain catalog/photo/stock management and can submit their own requests. Viewer remains read-only.

Approval does not reserve or deduct stock. An Admin's issue operation locks the request, item and balance, checks stock and request versions, and commits the actual issue, immutable ledger/request events, audit and notification records together. Returns enforce the outstanding quantity and original serial ownership. Borrowed serials cannot be manually restocked to bypass the request, and an item with an outstanding loan cannot be archived. Creation, issue and return use durable idempotency keys; action dialogs retain the original operation/version across retries. Users may cancel their own pending/approved request; after issue an Admin records returns. Concurrent cancellation and issue cannot both succeed.

## Production installation gates

1. Install Docker Engine/Compose and configure a resolvable server hostname. Generate `.env` with unique secrets; set a working SMTP URL and sender. Do not commit `.env` or reuse development credentials.
2. Review image provenance and pin release image digests after scanning. The supplied base-image major tags receive patch updates. The reference MinIO image builds pinned server/client source releases because the public registry images could not be fetched during verification. Both upstream community repositories are archived: review patch ownership and use a maintained, company-approved S3-compatible service for live operations. The reference source build has not been run in this workspace, which has no Docker. See [the upstream source-build instructions and security release](https://github.com/minio/minio/releases/tag/RELEASE.2025-10-15T17-29-55Z), [server repository](https://github.com/minio/minio), and [client repository](https://github.com/minio/mc).
3. Run migrations and seed with the owner credential. Run the application with the restricted `sdp_app` role. Confirm that runtime updates/deletes of ledger/audit/serial history are denied. Changing an initialized database's password in `.env` does not rotate its actual password; rotate database roles explicitly.
4. Keep SQL Server, MinIO, the app port and MinIO console off public interfaces. Allow only proxy 80/443, with administrative SSH access restricted independently. Set `APP_ORIGIN` exactly to the URL employees use. Use the supplied SQL Server bootstrap and separate migration/runtime accounts; do not run the app as `sa`.
5. The private-server Caddy configuration uses an internal CA. Distribute/trust the CA on managed clients; keep the CA private key protected. For a public DNS domain, remove `tls internal` and configure the approved ACME/certificate workflow. Verify HSTS and Secure/HttpOnly cookies in the real browser.
6. Confirm the retained display timezone and production name before entering real stock; these no longer have a Company details editor. Company identity stays SHINDENGEN ELECTRIC MFG.CO.,LTD. Pricing has been removed from screens and reports; historical database amounts are retained without being edited by item saves. Add approved logos/colors, regenerate icons, retest both themes, and verify the actual label printer/barcode scanner. The initial seed creates only the Admin in production unless sample data is explicitly enabled.
7. Run `npm test` with an isolated real `TEST_DATABASE_URL`, then the browser suite. Exercise concurrent issues, duplicate requests, timeouts/retries, role changes, reset emails, upload limits, PDF/CSV filters, and restoration from backup.
8. Configure structured-log collection and alert on readiness failures, reconciliation discrepancies, terminal outbox failures and storage exhaustion. Request logs intentionally omit bodies, query strings, passwords and tokens. Restrict access to database audit logs and development mail files.
9. Configure daily encrypted backups and a retention schedule appropriate to company policy. Run the restore drill below before accepting production data. Do not use `docker compose down -v` on live data.

## Backup and restore drill

Pause writes for a coordinated database/object snapshot. Take a SQL Server database backup with the authorized backup account and an object-store snapshot/mirror from the same window. Store the backup outside the SQL data volume, encrypt it and keep an off-host copy; record application commit/image digest, migration version and snapshot time. Verify the SQL backup and perform an actual isolated restore, rather than treating a copied live database file as a backup. Snapshot the Caddy data volume separately if retaining the private CA across replacement hosts. See `sql-server.md` for the database configuration and migration boundary.

Restore into an isolated server/network with email delivery disabled or redirected to a test mailbox. Restore the database, then the matching objects and deployment configuration; keep the same encryption/signature secrets if existing sessions must survive, or rotate them to force sign-in. Reapply runtime-role grants after restoring ownership. Run readiness, `npm run db:reconcile`, representative image reads, PDF generation, access-denial checks and a manual stock-in/out cycle. Only point real users to the restored service after these checks pass. Record measured recovery time and any lost-data window.

## Explicit verification limits

Container startup, S3/MinIO network access, production SMTP, TLS trust and backup restoration must be checked on the target server or in CI. The API and request workflow have been exercised on an isolated real SQL Server 2022 Express database; this does not replace installation checks on the intended server. Fast fallback tests using PGlite serialize transactions within one connection. A worker timeout and container memory limit reduce image denial-of-service risk; they are not a general sandbox for arbitrary uploaded code.
